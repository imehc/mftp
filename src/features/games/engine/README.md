# 对局引擎

此目录负责回合制小游戏的座位装配、输入调度、生命周期、观察投影和联机同步。游戏规则和电脑策略由各游戏 feature 提供，Rust 负责共用房间通信，不维护每个游戏的规则。

## 接入游戏

实现 `GameDefinition<S, M, P, O>`：

- `id`、`version`、`seatCount` 标识游戏、规则版本和座位数量。
- `currentSeat`、`applyMove`、`isFinished`、`outcome` 负责确定性规则及终局。随机游戏把可重放的种子或随机输入留在权威状态中。
- `observe(state, seat)` 返回该座位可见的观察。公开棋类可以投影完整局面；隐藏信息游戏只返回自己的手牌、公开事件和允许看到的对方信息。
- `P` 是表现数据，也必须符合接收座位的可见范围；规则状态不直接交给渲染。

使用 `ParticipantConfiguration` 按座位选择 `local`、`computer` 或 `remote`；`viewerSeat` 固定到参与者座位，同屏轮流可以设为 `active`。界面用 `participantCapabilities(adapters)` 判断可提供的方式，并分别持有每座位的难度或远端成员配置。

`createParticipantSession` 将配置交给同一个规则循环。电脑提供 `AiStrategy<O, M>`；远端通过已验证成员绑定控制器。不能把没有适配的方式显示为可用。已有两人菜单通过 `boardParticipantConfiguration` 转换旧模式，以保留存档和现有交互。

页面仅使用 `MatchHandle<O, M>`。完整状态及历史查询仅用于权威规则、持久化或协议适配；公开会话、恢复弹窗和普通控制器使用座位观察。`GameOutcome` 支持座位或团队胜者、平局、并列、排名和 JSON 自定义结果。

## 生命周期与兼容

公共中止信号携带应用隐藏、页面脱离、悔棋和会话销毁等结构化来源，不依赖 AI 配置或异常文字。暂停、重开和旧结果丢弃仍由统一对局循环管理。

小游戏当前支持本地玩家、电脑和远端玩家。历史模式 `ai` 表示本地算法电脑；模型对局存档不属于当前可运行模式，校验失败时保留原文件，不能自动转换成电脑。后续 AI 接入范围见独立统一参与者方案。

## 联机适配

多人回合制使用 `PartyAuthority` / `PartyReplica` 与 `PartyConnection`：

1. 房主运行完整规则，以本地、电脑或远端控制器装配座位。远端成员只能提交自己座位的动作。
2. 游戏提供 `PartyGameAdapter` 的动作合法性解析、公开事件和观察解析；公开事件不得包含未公开手牌、牌堆或随机种子。
3. 权威端广播提交，再分别向远端成员发送自己的观察、公开参与者摘要与结果。副本只持有本座位观察，不创建完整规则引擎。
4. `PartyConnection.attach()` 登记事件与后台生命周期；房主在事件监听就绪后 `start()`。后台暂停，前台由用户显式 `resume()`；远端恢复先请求当前观察。
5. socket 失效时显式调用连接的 `reconnect()`；恢复凭据在 Rust 内轮换、绑定稳定成员和原座位。旧连接和旧对局代次不能继续控制座位，未确认动作不会自动重放。
6. `dispose()` 停止前端交付及规则循环；离开房间用 `close()` 等待后端连接和 worker 排空。隐藏游戏悔棋默认禁止，只有游戏明确提供 `allowUndo` 政策才能回退。

协议支持最多 64 个座位、31 个远端连接；电脑在房主端运行。恢复限当前后端运行期、同设备，不包含跨进程恢复、跨设备转移、房主迁移或防房主作弊。

已有两人公开棋类通过 `ipc/game-room.ts` 使用同一成员传输，保留锁步和协商业务协议；军棋保留 `authority-v2` 的观察、悔棋和重赛政策。其页面仍按既有结束/重新加入流程处理断连；新多人会话使用上述副本恢复接口。

多人页面需要游戏自己的呈现适配，现有 `GameMatchDisplay` 仍用于两人；隐藏三人规则仅为逻辑样例，不是斗地主功能。
